# 失败分析

## 第三阶段复核：既有演化归因证据不足（2026-11-21）

旧 `_attribute_failure` 对每个未处理的目标检查所有同族活动规则；只要条件匹配便记 strike。它没有证明规则被检索、被 Agent 采用，或直接导致跳过。匹配是相关性，不能单独支撑因果归因。现已停止这种自动记过；历史数据和旧实验的 2/8、5/8 原样保留，但不能再将差异解释为已证明的精确因果归因。新的演化机制需要显式规则到执行决策的证据和独立验证。

按"现象 → 证据 → 根因 → 处置"组织。每条都指向具体文件/行或数据库查询。

## F1 合取规则任务两个模式都近乎全败

**现象**（上一阶段，18 任务）：`conditional` family A 0/6、B 1/6、D 0/6。

**证据**：
```
D 的 5 次失败全部是 targets_actioned 未完成（3/4、4/5），即少做了记录
→ 过度排除，不是漏做
```

**根因（已修正，原判断有误）**：最初的解释是"散文丢掉了连接词"。本阶段的实测推翻了它：
补上 `_cites_operand` 守卫与点名操作数的 prompt 之后，**散文模式 B 自己就能解对合取**（4/4）。
真正的原因是**经验文本里没有操作数**（模型写"检查例外标记"，不说哪些标记），
读者只能靠猜，猜错方向就过度排除。

连接词丢失是次生现象：当 lesson 里只有"gold"和"audit"两个词而没有结构时，
读者把它们当"或"处理是最自然的错误。

**处置**：`_cites_operand`（模型 lesson 不含判别性取值 → 回落到确定性提取器）+
结构化条件（把连接词变成数据）。见 `docs/STRUCTURED_MEMORY_DESIGN.md`。

## F2 完整生命周期 D 未优于朴素记忆 B

**现象**：B 11/18、D 10/18（p=1.0），D 多耗 19% token。

**证据**（`artifacts/live3/mode_D/memory.db`）：

| 用途 | 调用数 | 输入 token | 输出 token |
|---|---|---|---|
| act | 169 | 151,499 | 20,740 |
| extract | 18 | 23,894 | 8,310 |
| **critique** | **38** | 10,375 | 12,759 |
| **reconstruct** | **35** | 9,285 | 7,967 |

critique 的判定分布：apply 25、adapt 10、reject 1。

**根因**：**73 次额外调用里，35/36 次 critique 没有改变任何决策。**
调用本身还挤占了输出预算（reasoning 模型每次调用的输出 token 是输入的两倍多），
进而影响后续动作调用的可用预算。

**处置**：选择性 critique（`MemoryCritic(selective=True)`），三条触发条件之外不咨询模型。
实测在 4 个任务上把 critique 调用从约 2 次/任务降到 **0**。

**未验证**：降低调用数是否无损成功率，本阶段 n 太小。

## F3 结构化模式首次 live 运行：判定全对、一条记录都没写

**现象**：S 模式 2/8，比 B 还差。

**证据**（`artifacts/ablation_stepbug/mode_S`）：
```
trace 里 check_rule 逐条调用（r00,r01,r02,r03,r04...），verdict 全部正确，
但 set_field 调用数不足，任务在步数耗尽时结束。
```

**根因**：`check_rule` 一次只查一条记录，**每条消耗一个步骤**；
而 `Task.max_steps = 记录数 + 6` 是按"列表 + 写入 + 日志"估的，没给规则求值留余量。
模型把预算花在了求值上，没走到写入。

这是一个典型的"加了工具改变了步骤经济学"的失败——工具本身正确，配额没有跟着改。

**处置**：
1. `check_rule` 支持 `rids: list`，一次调用求值整批；
2. 结构化模式在有规则时额外给 4 步余额。

修复后 S 从 2/8 回到 6/8。

## F4 检索未按 family 过滤（上一阶段，已修）

**现象**：`conditional` family 在 D 模式下每个任务 `injected=0`，但该 family 有 6 条 active 经验。

**根因**：`index.search(goal, top_k)` 未传 family；conditional 的 goal 文本与 escalation 几乎相同，
top-3 被 escalation 经验占满，critic 再逐条以 family mismatch 拒绝，任务在零记忆下运行。

**处置**：`index.search(..., family=task.family)`。作废了当时一轮 658 次调用。

**教训**：critic 的 family 硬门是一个**兜底**，不是过滤器。把过滤职责放在检索层，
兜底才不会退化成"全部拒绝"。

## F5 reasoning 模型返回空 content

**现象**：部分调用 `content` 为空、`finish_reason='length'`。

**根因**：`deepseek-flash` 先产出 `reasoning_content`，`max_tokens` 被推理吃掉。
原实现把空 content 当作"模型拒答"，静默浪费一步。

**处置**：空 content + 非零 completion tokens → 抛带诊断的 `LLMError`；
动作预算提到 1200；历史截断到 9 条消息（推理开销随上下文增长）。

## F6 检索排序不稳定（上一阶段，已修）

**根因**：tie-break 用 uuid4。两次相同运行召回顺序不同，表现为 B=50% / C=58%（本应完全相同）。

**处置**：按文档文本 / 稳定插入序决胜负。
`tests/test_determinism.py::test_two_runs_are_identical` 盯住。
