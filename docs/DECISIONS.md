# 设计决策记录

## 第三阶段基线复核（2026-11-21）

- 回放结果分为 accepted、rejected、pending；unknown 与缺少正反例均不能视为通过。accepted 只表示与给定训练证据一致，不证明未来正确。目前独立组件尚未成为强制准入门。

- 新的面板准入只在红灯的任务作用域里回放封锁例外，避免把琥珀灯误当作应激活的反例；旧模式保留原有语义以维持历史对照。新版本在安全切换实现前不得激活。
- 停止把规则匹配漏处理记录直接当成因果归因；代价是目前无法自动按该信号退休经验。只有建立可追踪的规则到执行决策链后才能恢复。
- API 失败的用量若不可知，保留请求预留并停止后续付费调用，而不是按零计量；图像 token 预留为保守估算而非服务端硬保证。
- 对确定性阈值提炼仅在明确假设类下枚举候选；不能区分多个阈值时保留 pending，不把任意代表值当成已学到的规则。
- 新增单独标识的 `V2-threshold` 探索臂，利用训练评分标签在预设阈值假设类内选择边界读数；对照臂复用相同训练面板。其结果不等同于原计划的模型自由归纳或原始 V2-new。

- 保留历史面板生成器与原始结果，新的消融应使用消除位置规律的新数据版本；代价是不能把旧数据直接当成严格配对对照。
- 暂不启动付费实验：现有视觉脚本按臂分配预算，且失败响应的 token 可能未计入；需要先实现跨实验共享的预算约束和可审计的失败计量。
- 图像字体优先使用原 Linux DejaVu，其他系统依次回退到可用字体。渲染字节可能因平台不同而变化，跨平台实验须记录字体和图像哈希。

格式：每条决策给出**选择 / 被否掉的方案 / 理由 / 代价**。代价一栏是认真的：任何"没有代价"的方案都是没想清楚。

---

## D1. 存储用 SQLite 单文件，不用 Postgres / Milvus

**选择**：`sqlite3` + WAL + 版本化 schema。
**否掉**：Postgres（DevFlow 已有的选择）、Milvus（MemHarness 的选择）、向量库。
**理由**：这个项目的瓶颈是可审计性，不是吞吐。一次 run 一个 `.db` 文件，可以整包拷走、用 `sqlite3` 直接查、用 `git` 之外的任何方式比对。MemHarness 的 Milvus 路径在审计里暴露了两个问题：`update_records` 是 delete+reinsert，且**检索时对每条命中同步 update**，读被放大成写；每任务一个 collection 让跨任务分析变难。
**代价**：没有并发写能力；没有 ANN 索引，检索是精确线性扫描。在当前规模（几十到几千条）这是优势（结果可复算），超过 ~10⁴ 条就会成为瓶颈，届时需要替换 `ExperienceIndex`。

---

## D2. 自建确定性工具环境，不用 ALFWorld / WebShop / τ²-Bench

**选择**：`bench.py` 的记录运营环境，4 个工具，状态可完全比对。
**否掉**：三个参考仓库各自的 benchmark。
**理由**：它们的分数都依赖 GPU、Docker 或 LLM judge，在本机一个都跑不了；更重要的是它们的"成功"由 LLM judge 或用户模拟器判定，在本项目的规模下不可反驳。我需要一个**成功与否不依赖任何模型**的判据，否则"记忆是否提升了成功率"这个问题本身就问不清楚。
**代价**：任务分布极窄（两个 family、8-10 条记录），结论不能外推到真实任务。这是有意的取舍：先把机制做成可验证的，再谈泛化。

---

## D3. 只接受程序化验收，模型自评的成功一律丢弃

**选择**：`Outcome.verified_by` 区分 `program` / `model` / `none`；`ExperienceExtractor` 见到非 `program` 直接拒绝提取。
**否掉**：让模型判断任务是否完成（多数 agent 框架的默认做法）。
**理由**：项目简报明确要求"不能以模型自己判断成功代替客观验收"。这条如果只写在文档里就毫无约束力，所以它被写成了代码里的第一道闸：`test_extractor_refuses_model_judged_outcome`。
**代价**：只能评价有客观判据的任务；开放式任务（写作、设计）无法纳入。

---

## D4. 经验按版本存行，内容不可变

**选择**：`experiences` 主键 `(experience_id, version)`；`revise()` 产生新行；旧行标 `superseded`。
**否掉**：Recuris 的做法（包级目录不可变，卡片只能删）、MemHarness 的做法（记录不可变但 utility 可变）、CMA 的做法（无版本）。
**理由**：审计发现三者都回答不了"这条经验被改过几次、每次为什么改、改之前是什么"。RAI 场景下，一条被推翻的经验的**旧文本**本身是证据。
**代价**：表会随修订线性增长；查询需要区分"当前版本"与"历史版本"，`get()` 默认返回最新版，历史要用 `all_versions()`。

---

## D5. 证据内容寻址，派生表示单独成行

**选择**：`evidence/<sha[:2]>/<sha[2:]>`；缩略图/caption 是独立行 + `derived_from` 边。
**否掉**：按路径存（CMA）、按 doc id 缓存向量（Recuris）。
**理由**：两个反面教材都能在审计里指名道姓——CMA 的 `align_image_to_model` 原地 resize 覆盖原图；Recuris 的 embedding 缓存键只含 id 不含正文，`edit_card` 保留 id 时旧向量不会失效。内容寻址让这两种错误在结构上不可能发生。
**代价**：写放大（同一张图的三种表示占三份）；元数据不可改，第一写入者胜出。

---

## D6. 离线用哈希词袋向量，不下载 embedding 模型

**选择**：`HashEmbedder`（256 维，FNV-1a 哈希，L2 归一化）。
**否掉**：`bge-m3` / `sentence-transformers`。
**理由**：本机无 GPU、网络不稳、且下游一切结论都要可复算。哈希嵌入是**确定性**的，同一文本永远同一向量。它诚实的能力边界是：这是词法特征，不是语义。
**代价**：同义改写召不回来（"escalate" 与 "raise priority" 不匹配）。这是真实缺口，写进了 `INTEGRATION_DESIGN.md` 第 7 节。换成真模型只需实现 `Embedder` 协议两行。

---

## D7. 离线实验用确定性策略，结果标为 harness_selfcheck

**选择**：`ScriptedOpsPolicy` 是一个规则跟随器；结果的 `evidence_class` 字段写死 `harness_selfcheck`。
**否掉**：用脚本策略的增益当作"记忆有效"的证据。
**理由**：这是本项目最容易自欺的一处。脚本策略确实会读 `do not act on ... tier=gold` 这样的句子并照做——这证明了**管线通**，不证明**真实模型会因此变好**。所以证据等级被写进结果文件本身，`summary.md` 顶部的 warning 是自动生成的，无法忘记写。
**代价**：今晚没有任何"记忆提升真实模型成功率"的结论。这个结论必须等 API 实验，且即使那时也只有 12 个任务、MDE ≈ ±57pp。

---

## D8. Critic 对 family 不匹配直接 reject

**选择**：记忆的 `family` 与当前任务 `family` 不同 → `REJECT`。
**否掉**：允许跨 family 注入并要求模型自己判断适用性（MemHarness 的路线）。
**理由**：离线实验里 B 模式（无 critic）产生了 25% 的负迁移率，D 模式为 0——机制是可观测的。MemHarness 的审计结论正是"replay 会造成负迁移"，而它的抑制手段依赖一个训练出来的模型；本项目在没有训练条件时选择了确定性更强的那一侧。
**代价**：跨领域正向迁移也用不上。若将来 family 划分变细，会过度保守。

---

## D9. 不复制任何第三方代码

**选择**：三个仓库只读，全部模块自己写。
**理由**：CMA-Harness 无许可证且明确声明不授权；Recuris 与 MemHarness 是 Apache-2.0 但审计发现两者都有"文档声称、代码未接线"的机制，复制等于继承这些缺口。
**代价**：开发量大；很多轮子重造（BM25、RRF、bootstrap）。收益是每个机制都能指向自己的一条测试。

---

## D10. 检索索引按需全量重建

**选择**：`Harness._experience_index()` 在 active 数量变化时重建整个索引。
**否掉**：增量更新。
**理由**：正确性优先。增量更新需要处理"修订后旧向量失效"，正是 Recuris 栽的那个坑。当前规模重建成本可忽略（几十条）。
**代价**：规模上去后 O(n) 重建会成为瓶颈。阈值大约是几千条。

---

## D11. 排序的并列项按内容文本决胜负，不按 uuid

**选择**：`ExperienceIndex.search` 与 `BM25Index.search` 的 tie-break 用文档文本 / 稳定插入序。
**理由**：这是实际发生过的 bug。第一版按 `experience_id` 排序，而 id 是 uuid4，导致两次完全相同的运行召回顺序不同——B 模式 50%、C 模式 58%，而这两者在离线条件下应当**完全相同**。修好后两次运行逐位相同，`test_determinism.py` 盯着这件事。
**代价**：几乎没有；只是不能再拿 id 当稳定的排序键。

---

## D12. Token 预算在调用前检查，超了就抛异常

**选择**：`BudgetedLLM.complete` 先查 `calls+1 > max_calls` 与已消耗 token，超限抛 `BudgetExceeded`。
**否掉**：调用后统计、"软性"降级。
**理由**：项目简报给了 200 次 / 50 万 token 的硬上限。事后统计意味着你已经超了。中途抛异常会让实验结果不完整，但这比悄悄超支更可接受，且异常会被 trace 记录下来。
**代价**：长任务可能被硬中断；需要在 `NEXT_STEPS.md` 里记录未完成的实验。

---

## D13. 每个 family 的第一个任务注定失败——这是设计而非缺陷

**选择**：不回传任何先验规则，hidden rule 只能通过失败反馈学习。
**理由**：这是"记忆是否有用"的最小可测设定。如果第一个任务就能成功，说明任务本身不需要经验；如果所有任务都失败，说明经验无法被学到。D 模式 10/12 的构成正好是"两个 family 各失败一次，其余全部成功"。
**代价**：成功率的上限被结构性限制在 `(n - n_families) / n`；报告必须说明这一点，否则 83.3% 会被误读成"系统还不够好"。
