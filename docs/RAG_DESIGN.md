# 知识库 RAG：设计与实验结果

> 文档导入更新：新增 PDF 页面文字提取、图片与扫描页 OCR，以及 Markdown 本地图片引用和来源定位。OCR 后的文字进入文本索引，并非图片向量检索；安装、实测和局限见 `DOCUMENT_INGEST.md`。下文旧格式范围属于历史阶段记录。

> 交付复核：示例语料和问题在开发过程中经过迭代，以下指标是探索性结果，不是独立未见测试集上的泛化结论。后续代码修复了混合有效/无效引用被误判、空引用被计为有效等情况；历史结果文件保留原样。本次 Windows 环境尚未安装 fastembed，未独立复跑真实 embedding。

本文件记录文档知识库主链路的实现与实测结果。经验记忆部分的结论在
`docs/STAGE4_RESULTS.md` 与本文件 §3（两者边界）。

---

## 1. 做了什么

```
文档导入 → 解析与切分 → 建立索引 → 提问 → 召回片段 → 基于片段回答 → 带来源
```

| 模块 | 内容 |
|---|---|
| `src/evomemory/kb.py` | 文档库：导入、切分、三路检索、带引用回答、查询日志 |
| `src/evomemory/embeddings.py` | 三种 embedder：真实模型 / 词法哈希 / 测试替身，各自诚实标注 |
| `src/evomemory/kb_eval.py` | 固定问题集上的检索与回答评测 |
| `src/evomemory/kb_cli.py` | `import / search / ask / eval / demo` 五个子命令 |
| `data/kb_corpus/` | 8 篇构造文档（运维流程），约 6.7 KB |
| `benchmarks/kb_questions.jsonl` | 14 个固定问题（12 有答案 / 2 无答案） |

**存储边界**：知识库用独立的 `data/kb.db`，与经验记忆的 `memory.db` 没有共享表
（`tests/test_kb.py::test_knowledge_base_and_experience_store_do_not_share_tables`）。
文档是事实来源，经验不是。

## 2. Embedding：三种实现，只有一种是语义的

| 实现 | 是什么 | 标注 |
|---|---|---|
| `FastEmbedEmbedder` | **真实神经模型** `BAAI/bge-small-zh-v1.5`，512 维，ONNX | `semantic` |
| `LexicalHashEmbedder` | 已有的特征哈希向量（词法特征，不是语义） | `lexical` |
| `StubEmbedder` | 测试用关键词向量 | `stub` |

模型通过 `fastembed`（ONNX 运行时，**不依赖 torch**）在本地运行，文件缓存在
`cache/huggingface/rag/`，约 95 MB。不消耗 API 预算，不产生按次费用。

安装：`pip install 'evomemory[rag]'`。未安装时 `FastEmbedEmbedder` 抛出明确错误，
**不会静默退回哈希向量**——那正是本项目反复强调的"不要把词法特征说成语义检索"。

## 3. 实测结果

运行：`PYTHONPATH=src python -m evomemory.kb_cli demo --embedder fastembed --modes bm25,embedding,hybrid`
原始记录：`artifacts/kb/demo-20261121T094454266910Z-086c1c/results.json`

语料 8 篇 / 12 个 chunk，12 个 chunk 全部由真模型嵌入。问题 14 个，k=4。

| 检索方式 | Hit@4 | Recall@4 | MRR | 未命中 |
|---|---|---|---|---|
| BM25 | 0.917 | 0.917 | 0.875 | q11 |
| embedding（真模型） | 0.917 | 0.875 | 0.875 | q11；q13 只覆盖一半 |
| hybrid（RRF） | 0.917 | 0.917 | **0.917** | q11 |

回答检查（离线替身，`self_check`）：引用有效率 **1.000**，引用命中标准来源 **0.917**，
无答案问题的弃答率 **0.000**。

### 3.1 怎么读这张表

- **三个通道都没命中 q11**。"线上已经完全用不了了，第一步该做什么？"——正确文档的
  *另一个* chunk（讲复盘）排到了第 3，而含答案的 chunk 掉出 top-4。
  这是真实的困难样本，我没有为了让它通过去改语料或调权重。
- **在这个语料上 embedding 没有跑赢 BM25**（recall 0.875 vs 0.917），并在跨文档多片段
  的 q13 上少覆盖了一个来源。语料只有 12 个 chunk、问题与文档用词高度重合，BM25 本来就占优；
  这不能推广成"embedding 无用"，只能说明**在小规模、术语一致的语料上，语义检索的优势体现不出来**。
- **hybrid 的 MRR 最高（0.917）**，因为它不会因为某个通道排名靠后而丢掉本该靠前的片段。
- 语料小，全部指标属**探索性**，不做显著性声明。

### 3.2 弃答率为什么是 0

离线替身用"问题词元在最佳片段中的覆盖率"判断能否作答。实测这个信号**分不开**两种情况：

| 问题 | 有答案 | 词元覆盖率 |
|---|---|---|
| q08 耗尽预算之后还应该继续做什么 | 是 | 0.37 |
| q11 线上已经完全用不了了 | 是 | 0.41 |
| q09 数据库连接池应该配置多大 | **否** | 0.30 |
| q10 下周一值班的是谁 | **否** | **0.53** |

q10 与文档的重合度比两个可回答问题还高，因为它问的是"值班"——文档确实在讲值班，
只是没写具体是谁。**词面重合度无法区分"有答案"与"话题相关但缺答案"**。

因此替身只在近乎零重合时弃答（阈值 0.20），对其他无答案问题会照常引用最佳片段——
这是可测量的失败，写在 `tests/test_kb.py::test_overlap_alone_cannot_detect_a_missing_answer` 里，
不做调参掩盖。可尝试使用模型判断证据充分性，但模型也可能误判；本轮尚未验证。

## 4. 引用是怎么校验的

1. 检索到的片段按 `[1]..[k]` 编号，编号只存在于本次调用内。
2. 回答里出现的每个 `[n]` 都必须落在本次检索结果内；出现越界编号会在回答里附上
   "引用了未检索到的来源"的警告，并把该回答标记为 abstain。
3. 评测时另外检查：被引用的 chunk 是否真的包含该问题的标准来源短语。

引用**有效**（指向本次检索的片段）和引用**正确**（指向包含答案的片段）是两个不同的指标，
上表分开报告。

## 5. 与经验记忆的关系（当前集成程度）

已实现：两者并列存在，数据与表结构完全分开；回答中的事实引用只指向文档 chunk。

**未实现**：经验辅助文档检索（例如用经验调整检索策略或排序）。README 与报告里
不声称这一步已经完成。

一个容易混淆的点：经验被检索到 ≠ 回答有事实依据。经验只能影响"怎么做"，
不能充当"事实是什么"的来源。

## 7. 复现

```bash
pip install -e ".[dev,images,rag]"
export HF_HOME=$PWD/cache/huggingface/rag      # 模型缓存在项目内

# 只用 BM25，不需要模型
PYTHONPATH=src python -m evomemory.kb_cli demo --modes bm25

# 加上真实 embedding
PYTHONPATH=src python -m evomemory.kb_cli demo --embedder fastembed --modes bm25,embedding,hybrid
```

每次运行写入 `artifacts/kb/<label>-<时间戳>-<随机串>/`，不覆盖既有结果。
