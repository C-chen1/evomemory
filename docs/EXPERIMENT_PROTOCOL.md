# 实验协议

P4 交付物。本文件固定"怎样才算一次可信的实验"，后续所有实验按此执行。

---

## 1. 数据集划分

| 集合 | 用途 | 规则 |
|---|---|---|
| **Development** | 开发、调试、选参数 | 可以反复看 |
| **Memory Acquisition** | 执行经验提炼、写入记忆 | 经验只能从这里产生 |
| **Held-out Test** | 最终评测 | **绝不进入记忆写入流程** |

实现状态：
- `build_dataset(seed, per_family, families)` 生成时按 `seed` 偏移，开发集用 `seed < 100`，
  测试集用 `seed >= 1000`，两者记录表不同。
- 记忆写入只发生在 `Harness._write_memory`，它只看到当前任务；只要测试任务在一次独立 run 里执行，
  且该 run 的记忆初始为空，就不存在泄漏。
- **尚未实现**：自动化的跨集合泄漏检查（当前靠"一次 run 一个数据库"这一结构保证）。
  这是公认的缺口，记录在 §7。

### 1.1 独立性与聚类

一个 18 任务、3 个模板的实验，对"系统是否学会了规则"这个问题**有效样本量接近 3，不是 18**。
`metrics.effective_independence()` 会把 `n_templates` 显式写进结果文件：

```
independence: {'n_tasks': 8, 'n_templates': 2, 'tasks_per_template': {'escalation': 4, 'conditional': 4}}
```

所有报告必须同时给出**按任务族的拆分**（`by_cluster` / `paired_by_cluster_vs_A`），
不能只给一个汇总成功率——否则一个 hard family 的失败会被另一个 family 的成功掩盖。

## 2. 任务难度梯度

| 层级 | 规则形状 | family |
|---|---|---|
| L1 | 单属性排除 | `escalation`、`closure` |
| L2 | 合取（两属性同时满足） | `conditional` |
| L3 | 析取（由反例结构自动推断） | 由 `from_counterexamples` 覆盖，尚无专属 family |
| L4 | 否定 / 嵌套 | 谓词引擎已支持并测试，**任务尚未构造** |
| L5 | 过期规则、冲突规则 | **未构造**（U4/U5） |

L4/L5 的缺失是本阶段最大的空白：校验门（H4）只有在"记忆会变坏"的场景才能显示价值，
而这类任务一个都还没有。

---

## 3. 公平性固定项

同一批对照实验必须固定：

| 项 | 当前做法 |
|---|---|
| 模型 id | `settings.model`，单点配置，不由各模块自选 |
| 温度 | 0.0 |
| Prompt 版本 | 写入 `experiences.prompt_version` 与 `llm_calls.prompt_version` |
| 任务集 | 同一 `build_dataset` 调用 |
| 工具集 | 由 mode 决定，其余相同 |
| 步数预算 | `Task.max_steps`，结构化模式额外 +4（已在文档标注） |
| 输出 token 上限 | 动作 1200 / 提取 900 / critique 700 / 重建 600 |
| 记忆获取流程 | 同一个 extractor |
| 预算账本 | `BudgetedLLM` 单一入口，所有调用记录在 `llm_calls` |

**不固定、必须报告的**：模型服务端非确定性。temperature=0 不等于可复现，
因此重要对照需要重复运行，且不得因单次结果好坏而选择性保留。

## 4. 统计

| 指标 | 方法 |
|---|---|
| 每臂成功数 / 成功率 | 直接计数 |
| 逐任务配对差异 | `compare_paired` |
| 置信区间 | task-level percentile bootstrap（5000 次，seed=0） |
| 显著性 | **exact McNemar**（配对设计，比独立比例检验有力得多） |
| 按规则类型 | `paired_by_cluster` |
| 小样本 | 同时报告 `mde_binary(n)`，明确"此样本量下可检出的最小效应" |
| 主指标 / 主对照 | 预先固定为"成功率"，主对照为"记忆臂 vs 无记忆臂"；其余为探索性 |

禁止：事后挑选指标、把探索性结果写成主要结论、用测试集结果调参后再在同一测试集上报告。

---

## 5. 运行顺序

```
确定性测试（无需 API）
      ↓
脚本策略端到端（harness_selfcheck，验证管线）
      ↓
视觉/文本冒烟（1-3 次调用，验证链路与计量）
      ↓
小规模 live（≤20 次调用，确认无泄漏、预算生效）
      ↓
正式对照（按预算分批，可断点续跑）
```

`--run-dir` + 自动 resume 使长实验可以分批执行，且中断不会丢失已完成的任务。

---

## 6. 报告要求

每个实验必须给出：

1. `evidence_class`（`harness_selfcheck` / `live_model`）；
2. 模型 id、任务数、模板数、每模板任务数；
3. 每臂成功率 + 按族拆分；
4. 配对 delta、CI、McNemar p；
5. 实际 token 与调用数（含失败与重试）；
6. 作废/中断的实验及其原因与成本；
7. 明确写"这些结果不能说明什么"。

## 7. 已知缺口

| 编号 | 缺口 | 影响 |
|---|---|---|
| G1 | 无自动化泄漏检查 | 依赖"一次 run 一个库"的结构保证，没有测试兜底 |
| G2 | L4/L5 任务（否定/嵌套/过期/冲突）未构造 | H4 无法检验 |
| G3 | 未重复运行关键对照 | 无法区分效应与单次波动 |
| G4 | 视觉实验未运行 | H3 无数据 |
| G5 | 结构化与散文的对照与 prompt 变更混杂 | S vs B 的差异不能完全归因到表示 |
