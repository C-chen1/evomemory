## 1. 上一轮的归因链不够（已修正）

上一轮的三段链是「规则判豁免 + 没有 set_field + 评分器要求」。评论指出得对：**三者同时成立仍不必然证明
agent 是因为这条规则而跳过**——也可能是漏做、超时、步数耗尽。

现在拆成五件可分别记录的事：

| 事实 | 记录位置 |
|---|---|
| 规则被求值 | `rule_decisions(task, rid, experience, version, verdict)` |
| agent 看到结果 | 工具返回值在对话里，无需额外记录 |
| **agent 明确采用该规则** | `skip_decisions(task, rid, cited_experience, reason)` |
| 该记录确实没被改 | `task_actions` 无对应写操作 |
| 评分器认为本该处理 | `outcomes.checks` |

**评级**：

| 组合 | 记录为 | 能否退休经验 |
|---|---|---|
| 显式跳过 + 引用了这条规则 + 该规则判豁免 | strike（强） | **能** |
| 显式跳过但没引用，或引用了别的经验 | `attribution_weak` | 不能 |
| 完全没有动作（沉默） | `attribution_weak: omission` | 不能 |
| 没有规则被求值过 | `attribution_unknown` | 不能 |

为了让"明确采用"可记录，环境新增 `skip_record(rid, reason, because_experience)` /
`skip_zone(...)`：**刻意的跳过必须是一个动作，并且要说明理由**。

离线漂移实验在这个更严的标准下仍然成立：2/8 → 5/8，**2 次强归因、0 条弱证据、0 条未知、17 次显式跳过**。

> **验收修正（终稿）**：上表的 5/8 是**回放尚未接进主线**时的结果。终稿把
> `admit_with_replay` 接进 `_write_memory` 之后，同样场景变成 **2/8 vs 2/8**：
> 漂移后编码新规则的候选与旧证据冲突，被回放拒绝。退休机制本身仍然生效
> （2 次引用式 strike、退休 1 条），但系统不能靠它恢复。详见 `README.md` 的"演示 1"。

## 2. 版本切换与冲突（Q6/Q7）

- **事务**：激活新版本与取代旧版本现在在同一个 `BEGIN IMMEDIATE` 事务里。
  之前两步分开，进程若在中间死掉会留下**两个活跃版本**，检索可能把两版都注入。
  回归测试用注入失败的方式验证了回滚：新版本停在 `accepted`，旧版本仍是唯一 active。
- **冲突**：两条活跃规则对同一记录给出相反判断时，写入 `rule_conflicts`
  （裁决仍取并集，即保守方向），不再静默地偏袒其中一条。

## 3. 真实模型试点（P2）：一次有价值的负面结果

6 个任务、单个演化臂（无对照）、漂移点在第 3 个任务。预算 90 次调用。

**观察到的**：

- **23 次显式跳过，全部引用了具体经验（100%）**。这说明"必须引用才能归因"的契约在真实模型上可执行，
  不是只有脚本策略能满足。
- **0 次 strike**。逐任务看，失败原因是：
  - `escalation_01`：**多做了**——学到的规则只覆盖 `tier=gold`，当天还要排除 `note=hold`，模型遵守了前者、踩了后者；
  - `escalation_02/03`：**少做了**（missing r03/r02），且这些记录**没有任何规则判豁免**，属于漏做；
  - `escalation_04`：**没写日志**（侧效应遗漏）；
  - `escalation_05`：少做两条。
- 因此归因机制**正确地什么也没归因**：这次失败不是规则造成的。

**这条结果的含义**：严格归因不是"太保守所以不工作"，而是"这次确实没有可归因的规则性失败"。
它的代价是——**演化在这种失败结构下不会被触发**，而这正是本轮想要的诚实结论。

**没做的**：对照臂（无演化）。剩余预算 46 次不足以再跑约 90 次的一臂，
且试点已表明漂移阶段没有收敛（6 个任务全败），即使跑对照也无法隔离演化的作用。

## 4. 视觉任务：换成真正依赖历史的设计（P3，离线已验证）

面板任务在两个方向上都不成立（文字与判分冲突 / 限制可从文字+像素推出）。
新任务 `history_bench.py` 把推断通道拿掉：

> 一个红区**能不能**被激活，只取决于该区域在**先前任务里红过几次**（≥2 次即锁定）。
> 这个次数不在当前图片里，不在任务文字里，任何工具也查不到。

离线验证（`tests/test_history_bench.py`，12 个测试）：

| 检查 | 结果 |
|---|---|
| 灯色在像素里 | ✅ 逐点比对 |
| 历史不影响像素 | ✅ 同样的灯色 + 不同历史 → **图像字节完全相同** |
| 任务文字不含区域名、次数、历史字样 | ✅ |
| 工具无法查历史 | ✅ |
| 只看图的策略 | 前 2 个任务成功（无锁定），**后 2 个失败**（锁定区被打开） |
| 用历史的策略 | 4/4 成功 |
| 陈旧历史 | → 过度操作（把锁定区打开） |
| 夸大历史 | → 过度排除（漏做） |

写 goal 时我自己的措辞先泄了题（"earlier inspections 的次数不显示"），被泄漏测试抓到并删掉。

### 4.1 真实模型在这个新任务上的单例观察

4 个面板、单臂、无记忆：

| 面板 | 结果 |
|---|---|
| history-00（无锁定） | 通过 |
| history-01（无锁定） | 通过（中途一次空响应，动作已完成） |
| history-02（2 个锁定） | **空响应中断**，未行动，`log_written` 失败 |
| history-03（2 个锁定） | 跑完，**`locked_respected` = False** —— 把锁定区打开了 |

**这是环境区分力的证据**：真实模型在唯一一个跑完的锁定面板上确实过度操作。
但 **n=1**，只能说"方向符合预期"，不能说已经确立。
另一半面板被空响应吃掉，这是已知的调用可靠性问题，不是任务问题。

## 7. 需要用户决策的事

1. **是否追加预算**。要拿到一条可解释的演化对照需要约 200 次调用
   （两臂 × 6-8 任务，且当前空响应率约 25%，实际需要更多余量）。
2. **模型调用可靠性**。空响应来自 reasoning 把 1600 输出 token 吃满；
   把动作预算提到 3200 会显著降低失败率，但单次成本上升。这需要你确认是否接受。
3. 面板任务已经证明没有研究价值，是否同意把视觉方向完全转到历史依赖任务上。
